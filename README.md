# moneygo

个人账单归集与消费分析 Web 应用的交互原型。目标是导入微信支付、支付宝和招商银行的导出账单，归集多来源记录，并看清真实消费。

**当前版本：仅使用内置虚构交易的静态演示。** 没有真实文件解析、银行连接、AI 后端、登录、数据库或持久化。界面中的“导入”只载入内置样例；刷新页面会重置所有操作。请勿把当前版本用于真实财务结算，也不要向仓库提交真实账单。

## 已有功能

- 消费报告：月度净消费、分类占比、周趋势和同期比较
- 模拟导入：微信、支付宝、招商银行三个来源；月末样例按固定关联 ID 合并
- 待确认：重复候选、部分退款和待分类交易的交互处理
- 交易明细：按月份、分类、来源、类型及关键词筛选，并查看原始来源
- 统计口径说明、重置演示，以及适配手机和桌面的布局

演示中的关联和退款建议由固定样例提供，不代表已经实现通用的账单匹配算法。

## 本地运行

运行静态页面不需要安装 npm 依赖或构建工具。可直接打开 `dist/index.html`，也可以在项目根目录运行：

```sh
python3 -m http.server 5173 --bind 127.0.0.1 --directory dist
```

然后访问 <http://127.0.0.1:5173>。关闭终端里的服务即可停止。

## 检查与测试

需要 Node.js 22 或更高版本；测试使用 Node 内置测试运行器，无第三方依赖。

```sh
npm run check
npm test
```

测试在隔离的 VM 中执行原始 `dist/app.js`，用最小 DOM 替身验证样例统计、退款、重复关联、分类、筛选和导入顺序。它们是逻辑回归测试，不替代真实浏览器的视觉、键盘操作和无障碍检查。

手动验收建议：

1. 切换 8 月与 9 月，核对报告和明细金额；划转及还款不计入消费。
2. 关联重复候选，确认净消费不变；另记一笔时确认增加 ¥128.00。
3. 确认退款，净消费减少 ¥129.00；再次操作不得重复抵扣。
4. 以不同顺序载入三个来源，月末消费合计仅增加 ¥196.00。
5. 检查搜索、清空筛选、弹窗关闭、Esc、Tab 焦点循环和重置。
6. 在桌面和手机宽度检查布局；刷新后确认回到初始样例。

## 统计口径

- 净消费 = 消费金额 − 已匹配退款；按退款到账月抵扣。
- 支付平台与银行卡记录关联后只计一次金额，原始来源仍可追溯。
- 本人账户划转、信用卡还款不作为消费重复计入。
- 未匹配退款暂不抵扣，待分类消费仍计入总额。
- 9 月的同期比较使用两个月的 1–26 日，避免覆盖日期不同造成误读。

初始虚构样例的 9 月净消费为 ¥9,662.30；已抵扣退款 ¥99.00；划转与还款合计 ¥5,800.00。金额仅用于回归核对。

## 下一阶段

建议先完成能验证的账单处理闭环，再接入 AI：

1. **字段与解析**：确定统一交易结构、来源字段、币种、金额精度、时区与原始行追溯；用经过脱敏或完全合成的样例开发微信、支付宝和招商银行解析器。实际格式以用户提供的导出样例为准，不预设所有格式都已支持。
2. **导入与去重**：实现批次、文件指纹、稳定记录 ID、重复导入幂等性、解析错误和预览确认；先保证单来源可靠。
3. **归集与对账**：跨来源匹配保留解释和人工确认；覆盖部分退款、多次退款、跨月退款、划转与还款，不把不确定候选静默合并。
4. **本地持久化**：优先评估浏览器端解析与 IndexedDB，提供备份、恢复和清除流程；在实现前明确数据保存位置和隐私边界。
5. **分析与分类**：先使用可解释规则和可编辑分类，再评估是否需要 AI。引入外部 AI、云存储或账号服务前需明确数据发送范围、访问控制和成本，不默认上传账单。

## 隐私与开发约定

- 仓库只保留代码和明确标注的合成数据。真实账单、账号、姓名、凭据及用户数据库不得提交。
- `.gitignore` 是防误操作的辅助措施，不能替代提交前的内容检查，也无法自动隐藏已跟踪文件。
- 当前版本没有任何账单网络上传逻辑；未来功能不得把演示数据边界误写成已实现的安全保证。
- 金额正式实现建议以整数分存储，避免浮点误差；每个解析器和对账规则应先补测试。
- 尚未选择开源许可证，不应将本仓库理解为已授予公开使用或再分发许可。
